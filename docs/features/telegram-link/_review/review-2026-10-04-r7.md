## Findings

### Backend

| # | Finding | AC | Where | Verdict |
|---|---|---|---|---|
| K14 | An interrupted sign-out still makes the unlink fail. `signOut` catches `InterruptedException` and puts the interrupt flag back at once. `deleteOrClose` then runs the delete on that thread. Request threads are virtual (`application.yaml`, `spring.threads.virtual.enabled: true`), and on an interrupted virtual thread socket I/O throws `SocketException: Closed by interrupt`. So the JDBC delete fails, the Owner gets a 500, and the account is not deleted.<br>Both reviewers confirmed it: a JDK probe, and a temporary `UnlinkIT` case that ran `unlink` on a virtual thread got `TransactionSystemException: JDBC rollback failed` with the row still there.<br>The end state is consistent: the row is kept, the session is open and unmuted, and a retry works. But it breaks AC-113 ("still deletes everything when Telegram can't confirm"), the unlink KDoc (`LinkedAccounts.kt:66-67`) and T67's goal. The new `release` catch is almost never reached from `unlink`. Severity is low: today only shutdown interrupts a request thread. | AC-113, AC-111 | `backend/app/src/main/kotlin/telex/messaging/LinkedAccounts.kt:167-169`, reached from `:82-85` | Fix now: `signOut` returns `false` and records the interrupt instead of calling `interrupt()`; `unlink` puts the flag back in a `finally` after the delete, close and destroy. Add an `UnlinkIT` that runs `unlink` on a virtual thread with a sign-out that throws `InterruptedException`, and asserts the row is gone, `signOutConfirmed == false` and the flag is set on return. |
